# PR Portal 3.0 — คู่มือติดตั้งและส่งต่องาน

ชุดนี้พัฒนาจาก HTML, auth.js, config.js และ Google Apps Script ที่แนบมา ใช้ Google Sheets/Apps Script เดิมเป็นหลังบ้าน และ GitHub Pages สำหรับหน้าเว็บ ไม่ย้ายข้อมูลไปแพลตฟอร์มใหม่

## สิ่งที่ทำแล้ว

- หน้าเข้าสู่ระบบและหน้ารวมบริการโทนฟ้า–ม่วง การ์ดกระจก มีชื่อผู้ใช้มุมขวาบน ปรับตามจอมือถือ ไม่ใช้ภาพต้นแบบเป็นพื้นหลัง
- หลังบ้าน `admin.html` เลือกผู้ใช้และกำหนดสิทธิ์ “ทุกบริการ รวมบริการใหม่ในอนาคต” หรือ “เฉพาะรายการที่เลือก” ได้ อนุมัติ/ปฏิเสธคำขอใหม่ได้
- เพิ่ม/แก้ไขบริการ ชื่อ คำอธิบาย ไอคอน ลำดับ เปิด–ปิด และเลือกไฟล์ HTML ที่อยู่ในรายการไฟล์ของเว็บ
- บังคับตรวจบทบาทและสิทธิ์ที่ API จากเซสชันจริง ป้องกันการแก้ role ในเบราว์เซอร์เพื่อเป็นแอดมิน
- ลืมรหัสผ่าน: ส่งรหัสชั่วคราว 28 ตัวอักษร มีอักษร ตัวเลข และเครื่องหมาย ใช้ตั้งรหัสใหม่ได้ครั้งเดียว ภายใน 15 นาที ไม่สามารถใช้เป็นเซสชันปกติได้
- OTP 6 หลัก อายุ 5 นาที ผูกกับคำขอและอุปกรณ์ จำกัดการลอง 5 ครั้ง การส่งซ้ำอย่างน้อย 60 วินาที และไม่เกิน 3 ฉบับต่อ 15 นาที
- ส่งรหัสในไฟล์แนบ `PR-Portal-access.txt` หัวข้อและเนื้อหาอีเมลไม่มีรหัส ห้ามอ้างว่าซ่อนการแจ้งเตือนได้ทุกเครื่อง
- การรีเซ็ตรหัสสำเร็จยกเลิกเซสชันและ OTP เดิมทั้งหมด มีการตรวจรหัสใหม่ซ้ำที่หน้าเว็บ
- ใช้ PBKDF2-HMAC-SHA256 600,000 รอบพร้อม salt และ server pepper สำหรับรหัสใหม่ เก็บ session/OTP/reset เป็น digest; ไม่มี default admin/password
- ล็อกการเขียนพร้อมกัน ตรวจเวอร์ชันก่อนบันทึก ปฏิเสธการเขียนทับข้อมูลใหม่จากหน้าจอเก่า มี audit log ไม่มีรหัสลับใน log

## สถานะที่ต้องทราบก่อนติดตั้ง

ไฟล์พร้อมสำหรับนำไปติดตั้ง แต่ยังไม่ได้แก้ Google Sheets, Deploy Apps Script, ส่งอีเมลจริง หรือ push Git ของคุณ การทดสอบที่แนบเป็นการจำลองบริการ Google ในเครื่อง ไม่ใช่การรับรองการใช้งานจริงทุกสภาพแวดล้อม

หน้าบริการสื่อและแบบสอบถามยังมีฟังก์ชันตัวอย่างตามไฟล์เดิม เช่น ตัวเลขวิเคราะห์ การโหลด Google Sheets และส่งออกรายงานที่ยังไม่เชื่อมข้อมูลจริง ชุดนี้เพิ่มการตรวจสิทธิ์ให้ทั้งสองหน้าและแก้การแสดงชื่อไฟล์ที่อาจแทรก HTML ไม่ได้สร้างตัววิเคราะห์/รายงานใหม่

HTML ที่อยู่บน GitHub Pages หรือ repository สาธารณะยังดาวน์โหลดหรือเปิด source ได้ ตัวตรวจในหน้าเว็บช่วยควบคุมการใช้งาน UI เท่านั้น ข้อมูลสำคัญต้องอยู่หลัง API ซึ่งเรียก `requireService_` ทุกครั้ง อย่าใส่ข้อมูลลับใน HTML/JavaScript/JSON/ไฟล์แนบใน Git หากต้องป้องกันแม้แต่ตัว HTML ต้องเปลี่ยนไปใช้โฮสต์ที่ตรวจสิทธิ์ฝั่งเซิร์ฟเวอร์

## 1. สำรองก่อนอัปเดต

1. สำเนา Google Sheets เดิมและโค้ด Apps Script ทุกไฟล์ เก็บ deployment version เดิม
2. สำรอง Git หรือทำ branch สำหรับอัปเดต
3. ตรวจหัวตาราง Users: `username, password_hash, salt, email, role, display_name, status, position, purpose, created_at` โค้ดอ่านด้วยชื่อคอลัมน์ ไม่เปลี่ยนลำดับหรือลบคอลัมน์เดิม
4. ตรวจบัญชีผู้ดูแลจริงว่ามี `role=admin`, `status=active` และอีเมลที่รับได้ ห้ามใช้ `your-email@gmail.com` จากตัวอย่างเดิม ให้เจ้าของชีตแก้เป็นอีเมลจริงก่อน
5. ตรวจไม่ให้ username หรือ email ซ้ำกัน ต่างตัวพิมพ์เล็กใหญ่ก็นับว่าซ้ำ บัญชีที่ไม่ใช่ `active` จะเข้าสู่ระบบไม่ได้

## 2. ตั้งค่า Apps Script

ใช้ Script Project เดิม แต่แทนที่โค้ด backend เดิมทั้งหมดด้วย `backend/Code.gs` และสร้างอีกไฟล์ `Crypto.gs` โดยวางเนื้อหาจาก `backend/Crypto.gs` ด้วย ห้ามเก็บ `doPost` เดิมซ้ำในโปรเจกต์

ไปที่ Project Settings → Script properties แล้วเพิ่ม:

| ชื่อ | ค่า |
|---|---|
| SPREADSHEET_ID | ID ของชีตเดิม จากค่าที่อยู่ในโค้ด backend เก่า |
| PORTAL_SECRET | ค่า hex สุ่มอย่างน้อย 64 ตัวอักษร สร้างตามคำสั่งด้านล่าง |

สร้าง secret ที่เครื่องตัวเองด้วย Node.js แล้วคัดลอกผลไปใส่ Script Properties เท่านั้น:

```sh
node tools/generate-secret.mjs
```

อย่านำค่าที่ได้ลง Git อีเมล หรือส่งในแชต เก็บสำรองอย่างปลอดภัย การเปลี่ยน/สูญเสีย secret จะทำให้เซสชันและรหัสผ่านที่สร้างด้วย secret เดิมตรวจสอบไม่ได้ ผู้ใช้ต้องรีเซ็ตผ่านอีเมลอีกครั้ง

รัน `migratePortal()` ด้วยบัญชีเจ้าของสคริปต์หนึ่งครั้งและอนุญาตสิทธิ์ Sheets/Email ที่จำเป็น ฟังก์ชันนี้สร้างชีต Services, Access, Challenges, RateLimits, Audit หากยังไม่มี ไม่ลบบัญชีเดิม ไม่สร้างแอดมินรหัสเริ่มต้น และจะยกเลิกเซสชัน/OTP รุ่นเก่าเฉพาะการย้ายครั้งแรก

ผู้ใช้เดิมทั่วไปเริ่มจาก “ไม่ให้สิทธิ์บริการใด” แอดมินเห็นบริการที่เปิดทั้งหมด บัญชีรหัสแบบเก่าจะต้องกดลืมรหัสผ่านเพื่อตั้งรหัสใหม่ก่อนเข้าสู่ระบบ ไม่ยอมรับรหัสเก่าเป็นเซสชันใหม่ รวมถึงรหัส `admin1234` จากชุดเดิม

ตั้ง time-driven trigger เรียก `cleanupPortal` ทุกชั่วโมง เพื่อล้างเซสชัน/รหัส/รายการจำกัดอัตราที่หมดอายุ และลบ audit เกิน 90 วัน

Deploy → Manage deployments → Edit → New version โดยใช้ Web app เดิม ตั้ง Execute as เจ้าของสคริปต์ และให้หน้าเว็บที่ไม่ได้ลงชื่อเข้า Google เรียกได้ (หากนโยบาย Workspace อนุญาต) ตัว API ตรวจการล็อกอินและสิทธิ์เอง ห้ามแก้นโยบายองค์กรเพื่อข้ามข้อจำกัด หากองค์กรไม่อนุญาต ให้ผู้ดูแลระบบเลือกวิธีโฮสต์ API ที่รองรับ

ตรวจ `web/js/config.js` ว่า API_URL เป็น URL `/exec` ของ deployment นี้ ห้ามใช้ `/dev` และห้ามใส่ secret ลง config

## 3. นำหน้าเว็บขึ้น GitHub Pages

ทางที่แนะนำ: วางโครงสร้างใน ZIP ไว้ที่ราก repository โดยคงโฟลเดอร์ `web`, `tools`, `.github` และ `backend` ตามเดิม ไม่มีข้อมูลชีตหรือ secret อยู่ใน backend source

ใน GitHub Settings → Pages เลือก Source เป็น GitHub Actions แล้วใช้ `.github/workflows/pages.yml` ที่ให้มา ตั้งชื่อ branch `main` หรือแก้ใน workflow ให้ตรงกับของคุณ Workflow สร้างรายการบริการ ตรวจไฟล์ แล้วเผยแพร่เฉพาะ `web/` การเพิ่ม HTML ภายหลังจึงไม่ต้องกรอกรายการไฟล์ด้วยมือ

หาก repository มี workflow Pages เดิม ให้ปรับหรือแทนที่อย่างระมัดระวังให้เหลือผู้ deploy เพียง workflow เดียว ห้ามใช้งาน workflow ทั้งสองแข่งกัน

ทางเลือกเมื่อใช้ Pages แบบเดิมจาก root: รันคำสั่งต่อไปนี้แล้วคัดลอกเฉพาะเนื้อหาภายใน `web/` ไป root ของพื้นที่เผยแพร่ โดยไม่ใช้ workflow ที่ให้มา:

```sh
node tools/generate-manifest.mjs
node tools/validate.mjs
```

ทางเลือกนี้ต้องรัน generate-manifest ใหม่ทุกครั้งที่เพิ่ม/ย้าย/ลบ HTML

เปิด URL เว็บไซต์ผ่าน HTTPS ห้ามเปิด `file://` เพื่อทดสอบ API หน้า `index.html` ส่งต่อไป `login.html` อัตโนมัติ ชื่อไฟล์ login เดิมที่แนบว่า `index (2).html` ถูกแทนด้วยหน้า `login.html` ในชุดติดตั้งนี้

## 4. การเข้าใช้ครั้งแรก

1. แอดมินเปิดหน้าเข้าสู่ระบบ → ลืมรหัสผ่าน → กรอกอีเมลจริงที่อยู่ในชีต
2. เปิดอีเมลและไฟล์แนบ นำรหัสชั่วคราวกรอกในฟอร์มตั้งรหัสใหม่ ตั้งรหัสอย่างน้อย 15 ตัวอักษร แนะนำวลียาวไม่ซ้ำระบบอื่น
3. เข้าสู่ระบบด้วย username เดิม + รหัสใหม่ แล้วกรอก OTP จากไฟล์แนบอีเมลอีกฉบับ
4. เปิด “จัดการระบบ” → เลือกผู้ใช้ → กำหนดสิทธิ์ → บันทึก
5. บัญชีสมัครใหม่ใช้ “อีเมลเต็ม” เป็น username เพื่อหลีกเลี่ยงการชนกันของชื่อหน้า @ คนละโดเมน หลังอนุมัติระบบส่งรหัสชั่วคราวให้ตั้งรหัสเอง

หากส่งอีเมลหลังอนุมัติล้มเหลว ระบบแจ้งแอดมินตรง ๆ บัญชียังคงอนุมัติแล้ว ให้ผู้ใช้กดลืมรหัสผ่านอีกครั้งหลังแก้ปัญหาอีเมล

## 5. เพิ่มบริการด้วย HTML

1. คัดลอก `tools/service-template.html` เป็น `web/service-example.html` และแก้ชื่อ/เนื้อหา ใช้ชื่อไฟล์ภาษาอังกฤษ ตัวเลข ขีดกลาง หรือขีดล่าง
2. คง script config/auth/ui/service-guard และเริ่มโหลดข้อมูลเมื่อได้รับ event `portal:authorized` หากมีโฟลเดอร์ย่อย ปรับ relative path ของ CSS/JS ทุกตัว และลิงก์กลับ dashboard ให้ตรง
3. ถ้าบริการเรียก API ข้อมูลจริง เพิ่ม action ใน `route_` ฝั่ง Apps Script โดยเรียก `requireService_(body, 'รหัสบริการ')` ก่อนอ่านหรือเขียนข้อมูลใด ๆ เสมอ ดู `API-AND-SECURITY.md`
4. อัปโหลด HTML และไฟล์ประกอบเข้า Git รอ Actions สำเร็จ หน้าเพิ่มบริการจะเห็นรายการจาก `services-manifest.json` หากไม่มี guard ระบบตรวจไฟล์จะไม่ยอมเผยแพร่
5. เข้า “จัดการระบบ → จัดการบริการ → เพิ่มบริการ” ระบุรหัสบริการไม่ซ้ำ เช่น `library-news` เลือกไฟล์ ไอคอน และลำดับ แล้วบันทึก
6. ผู้ใช้แบบ “ทุกบริการ” เห็นบริการที่เปิดใหม่ทันที ผู้ใช้แบบเลือกเฉพาะ ต้องติ๊กเพิ่มให้แต่ละคน

รหัสบริการคงที่หลังสร้าง ใช้เป็นตัวอ้างอิงสิทธิ์ เปลี่ยนชื่อหรือไฟล์ได้ ส่วนการนำออกให้ “ปิดใช้งาน” ก่อนเพื่อไม่ทำลายรายการสิทธิ์ย้อนหลัง

อย่าอัปโหลด HTML จากบุคคลที่ไม่เชื่อถือ เพราะ JavaScript ใน origin เดียวกันสามารถเข้าถึงเซสชันของเว็บไซต์ได้ การตรวจว่ามี guard เป็นเพียงการตรวจรูปแบบ ไม่ใช่การตรวจความปลอดภัยของโค้ดทั้งหมด

## 6. อีเมลและการแจ้งเตือนมือถือ

หัวข้อ เนื้อหาอีเมล และชื่อไฟล์แนบไม่มี OTP หรือรหัสชั่วคราว รหัสมีเฉพาะในไฟล์แนบที่ผู้รับเปิดอ่าน วิธีนี้ลดการเผยรหัสในพรีวิวทั่วไป แต่ผู้ส่งไม่สามารถบังคับ Mail/Gmail/Outlook หรือระบบสรุปข้อความของมือถือได้ ไฟล์แนบไม่ใช่ไฟล์เข้ารหัส และผู้ที่เข้ากล่องจดหมายได้ยังอ่านรหัสได้

ให้ผู้ใช้ตั้งค่าซ่อนเนื้อหาการแจ้งเตือนอีเมลบนหน้าจอล็อกด้วย บางองค์กรอาจบล็อกไฟล์แนบหรือส่งเข้าสแปม ต้องทดสอบบนอุปกรณ์/แอปที่ใช้จริง

รหัสชั่วคราวใช้เพื่อเปลี่ยนรหัสเท่านั้น รหัสจริงใหม่ไม่ส่งทางอีเมล การขอรหัสชั่วคราวไม่ล็อกบัญชีหรือเปลี่ยนรหัสเดิมจนกว่าจะยืนยันสำเร็จ การแจ้งรับคำขอใช้ข้อความเดียวกันทั้งอีเมลที่พบและไม่พบ โดยระยะเวลาตอบอาจต่างกันตามการส่งเมล

## 7. ตรวจรับก่อนเปิดให้ทุกคนใช้

- ทดสอบบนชีตสำเนาและ deployment ทดสอบก่อน โดยเปลี่ยน SPREADSHEET_ID/API_URL ให้ตรง
- ทดสอบแอดมิน ผู้ใช้เลือกบางบริการ ผู้ใช้ทุกบริการ และผู้ใช้ไม่มีสิทธิ์
- ใช้สองหน้าจอแก้สิทธิ์เดียวกัน ตรวจว่าหน้าจอเก่าถูกปฏิเสธด้วย CONFLICT และโหลดใหม่ได้
- เปิด URL บริการตรงด้วยบัญชีไม่มีสิทธิ์ และตรวจ API จริงของบริการว่าปฏิเสธด้วย ไม่ตรวจเพียงปุ่ม
- ตรวจ reset/OTP ในอีเมลจริง การใช้ซ้ำ รหัสผิด 5 ครั้ง หมดอายุ และเซสชันเก่าหลัง reset
- ตรวจ Google Mail quota/สแปม/นโยบายองค์กร ระหว่าง Apps Script ทำ PBKDF2 อาจใช้เวลาหลายวินาที และทำรายการพร้อมกันจะคืน BUSY ให้ลองใหม่ ไม่ส่งคำขอเขียนซ้ำอัตโนมัติ
- ทดสอบจอมือถือ แป้นพิมพ์ และเบราว์เซอร์ที่ใช้จริง ชุดนี้ยังไม่ได้ทดสอบหน้าจอด้วยเบราว์เซอร์

เหมาะกับพอร์ทัลองค์กรขนาดเล็กถึงปานกลาง ไม่ได้ผ่าน load test ระบบ Sheets ใช้การอ่านตารางและ global lock จึงไม่เหมาะกับผู้ใช้พร้อมกันจำนวนมาก หากมีโหลดสูงควรย้าย identity/database ไปบริการที่ออกแบบมารองรับโดยเฉพาะ แทนการลดความเข้มของการแฮชรหัสผ่าน

## ทดสอบในเครื่อง

ต้องมี Node.js 22 ขึ้นไป ไม่ต้อง npm install:

```sh
node tools/generate-manifest.mjs
node tools/validate.mjs
node tests/backend.test.cjs
```

`Crypto.gs` ถูก bundle ไว้แล้ว ใช้ hash.js 1.1.7 และ dependency ที่มีในสภาพแวดล้อมเดิม ไม่มีการดาวน์โหลดเพิ่ม ไม่ต้องรัน bundle-crypto.cjs เพื่อติดตั้งตามปกติ ดูประกาศสิทธิ์ใน `backend/THIRD-PARTY-LICENSES.txt`
